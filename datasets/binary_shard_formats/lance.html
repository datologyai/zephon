Lance¶

Lance is a columnar format with fast random access, wrapped in a versioned table format. A Lance dataset is a directory, not a flat collection of shards: it holds its data files under data/, and one immutable manifest per version under _versions/. The manifest lists every fragment — a horizontal slice of the dataset with its own data file and row count.

How Lance maps onto shards. One fragment is one Zephon shard. The mapping is forced in both directions: a fragment cannot be split across shards, because two shards would then resolve the same cached file, and two fragments cannot be merged into one shard, because they are two separate files. You control shard size when you write the dataset, through max_rows_per_file.

Because the manifest already records each fragment’s file, byte size and row count, it is the index: Zephon discovers a Lance dataset in two range reads, with no index.json to build and without opening a single data file. python -m zephon.build_index therefore has no Lance mode.

Preparing Lance datasets. Install Zephon with the lance extra, which adds the pylance dependency:

examples/guide/datasets/lance_install.sh¶
# Install Zephon with the lance extra.

pip install "zephon[lance]"
examples/guide/datasets/lance_write_shards.py¶
"""Write a small Lance dataset, one fragment per shard."""

import lance
import pyarrow as pa

table = pa.table(
    {
        "id": pa.array(range(8), pa.int64()),
        "text": pa.array([f"record {i}" for i in range(8)]),
    }
)

# Each fragment becomes one Zephon shard, so max_rows_per_file sets the shard size.
lance.write_dataset(table, "data/lance_demo", max_rows_per_file=4)

Reading Lance datasets in Zephon. Pass the dataset directory to Dataset.from_path, with or without fmt="lance":

examples/guide/datasets/lance_dataset.py¶
"""Define and inspect a Lance Dataset."""

from zephon.debug import DatasetInspector
from zephon.io import Dataset

# Discovery reads the dataset's newest manifest and pins to it, so dataset.path
# names that version: later appends do not change this run's shards.
dataset = Dataset.from_path("lance_demo", "data/lance_demo", fmt="lance")
print(dataset.path)

with DatasetInspector(dataset) as inspector:
    print(inspector.read(shard_id=0, sample_index=0))

Sample payloads are dictionaries keyed by column name, following the same conversion rules as Parquet.

Versions are pinned at discovery. A Lance dataset directory is mutable — an append creates a new version — while each manifest is immutable. Dataset.from_path resolves the directory to its newest manifest and makes that manifest the dataset’s path, so every rank and every worker in the run plans against exactly one version, however the directory changes underneath. Keep dataset.path if you want a later run to resume against the same shards; pass a manifest directly to read an older version:

examples/guide/datasets/lance_pin_version.py¶
"""Pin a Lance dataset to an earlier version by naming its manifest."""

from zephon.io import Dataset

# Any committed manifest under _versions/ is a valid dataset root. Passing one
# reads that version, which is what resuming a run against the same shards needs.
dataset = Dataset.from_path(
    "lance_demo", "data/lance_demo/_versions/18446744073709551614.manifest"
)
print(dataset.shard_count(), dataset.total())

Deleted rows. Lance deletes rows by recording tombstones rather than rewriting data files. Zephon reports the surviving row count per shard and maps each row it reads past the deleted ones, so a dataset you have called delete() on reads correctly and needs no compaction.

Upgrade Zephon

Caching reads. Zephon keeps each fragment’s decoded column mapping and tombstones per fetch replica, up to metadata_cache_entries (zero disables this). Files are not kept open between reads.

pipeline.options(io_options={"metadata_cache_entries": 256})

Worker threads. pylance starts one thread per core in every process by default. Zephon caps its pools at two workers: pylance decodes on them rather than on the fetch threads, so a single worker slows large reads. You can change the count through the pipeline’s io_options:

pipeline.options(io_options={"lance": {"worker_threads": 2}})

pylance sizes its pools once per process, so the count applies only if nothing in the process has used pylance yet, including writing the dataset. TOKIO_WORKER_THREADS and LANCE_CPU_THREADS from your environment win unless you pass worker_threads; None leaves the existing pool configuration unchanged.
