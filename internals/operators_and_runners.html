Operators and runners¶

How pipelines run claims an operator running across sixteen workers makes exactly the same decisions it would have made on one. This page explains the two pieces of machinery that deliver that, and what they ask of your operator in return.

The operator contract. An operator is a unit of transformation such as tokenizing, packing, batching or shuffling, and it neither knows nor cares how Zephon executes it. The three most important methods are:

  • accumulator(*, deterministic, ctx) returns the accumulator that decides how incoming elements are grouped into micro-batches. The deterministic flag comes from the runner and controls whether time-based flushing is allowed.

  • process_many(elems) is the workhorse, and the part that runs in parallel. It takes a micro-batch and returns a list of the same element types, which are SampleRecord objects, or SampleBatch objects downstream of batch(). To transform a sample you rebuild its payload while preserving its meta, which carries the identity and ordering that Records and sample lifecycles describes. Returning a bare dict or a raw payload gets you a TypeError: Unsupported element type.

  • traits() declares the OpTraits that guide compilation and scheduling, including the all-important preserves_cursor_order.

Three additional methods complete the contract. setup(ctx) runs once before any data arrives and receives an OpContext with runtime services and plan metadata, while process_one(elem) handles a single element and by default just calls process_many with a one-element list. You only want to override process_one if you have a faster scalar path. Finally, teardown() releases what setup acquired; its default is a no-op.

Teardown lifecycle. Runners, not operators, decide when teardown() runs:

  • Every runner calls it on each operator instance when the runner closes, and on any instance whose setup raised. Implementations must therefore tolerate partial setup and repeated calls.

  • Closing is permanent. After close(), run() and run_one() raise RuntimeError.

  • The inline and thread runners never tear down an instance in the middle of a call. On hard shutdown they tear down idle instances immediately and busy ones as soon as their current call returns. Callers of run_one() must not overlap it with close(). Inline graceful close also defers teardown if its execution wait exceeds the cleanup budget.

  • Process workers run teardown() in the worker as it exits, and Ray actors receive a short teardown call before they are killed. A worker that is terminated outright skips it, so teardown() is cleanup, not a place for work that must happen.

  • Cache release inside teardown waits on the cache’s .reset.lock for at most 1 s (100 ms on hard shutdown), counted from the start of that runner’s teardown. If the wait times out, the release is queued to a background thread. GC finalizers only ever queue. On normal exit, both modes give the worker up to 1 s more to catch up, then exit even if cleanup is still stuck.

The invariant is that process_many must be stateless across calls. It must not depend on anything left over from a previous invocation, so every piece of cross-invocation state belongs in the accumulator instead. This is the whole reason Zephon can safely hand process_many calls to an arbitrary number of workers: each call is independent, so the results can be reordered back into input order without loss of correctness.

Not every operator splits its work evenly between accumulator and workers. For tokenization or fetching, the accumulator does nothing but group elements into fixed-size micro-batches, and all the real work happens in process_many across the pool. For operators whose core logic is inherently serial, such as packing, mixture correction and shuffling, the accumulator does the heavy lifting and process_many is currently a passthrough that returns its input unchanged. Some of that work, like assembling packed payloads, is stateless in principle and could move onto the workers; we have not done it yet, and it is a throughput limitation on our side rather than something the design requires. What the design does require is that any logic needing to see elements in stream order lives in the accumulator.

Micro-batch sizes. How pipelines run introduces the micro-batch as the small group of elements Zephon hands to a worker for a single process_many call. Their sizes are per-operator, chosen for the work involved: fetching and tokenization use 64, text decoding uses 128, a map_transform uses 64, and batch uses whatever microbatch_size requested. With four workers on a tokenizer, four micro-batches of 64 are in flight at once, so 256 samples are being tokenized concurrently while each call still sees a sensible 64.

Who decides the boundaries? That is the accumulator’s job.

Accumulators. An accumulator is a small, single-threaded object that sits between an operator’s input stream and its worker pool. It receives elements from upstream in order, decides when enough of them are ready, and hands a micro-batch off to be dispatched.

What we guarantee is that it runs serially: the runner never calls into it from two threads at once, and elements always arrive in upstream order. The threads and process runners drive each accumulator from a single thread of its own, and the inline runner runs everything on the calling thread. The accumulator is never invoked in parallel with itself. The workers run the stateless process_many, and the accumulator decides what each worker sees.

Why accumulators matter for determinism. Take sequence packing. The packer keeps open bins, which are partially filled sequences waiting for short samples to complete them, and which bin a given sequence lands in depends on what is already in the bins. If each worker kept its own bins, the bin assignment would depend on which worker happened to receive which sample, which is to say on thread scheduling, and one worker and four workers would produce different packed sequences. Instead every bin lives in the packing accumulator, which sees elements in stream order on one thread, so the stateful decision always comes out the same way. The same argument applies to batching, mixture correction and shuffle buffering.

The bins are also per-lane, which is what connects this to elastic determinism: samples from different lanes are never packed together, so each lane’s packing decisions are independent of how many GPUs you are running on.

The interface. The accumulator has a simple interface with four methods and a flag, defined in zephon.ops.accumulators:

  • push_many(elems) consumes elements from upstream, buffers them, and returns zero or more ready micro-batches.

  • flush(*, reset=False, lane_id=None) emits what is still buffered, in one of two contexts. At end of stream (reset=False, lane_id=None) every lane is finished and any remaining partial micro-batches go out. Mid-stream (reset=True, with a lane_id) a flush sentinel has arrived, and your accumulator must emit and fully reset that one lane’s state while leaving every other lane untouched. Zephon injects flush sentinels per lane, so flushing every lane at one lane’s boundary corrupts the others and breaks replay.

  • has_pending_data(lane_id=None) reports whether a flush would produce anything, which the runner uses to avoid terminating early and to detect stalling.

  • try_epoch_reset(boundary_chunk_id, lane_id) asks whether a stalled sentinel can now be released, by asking whether your accumulator’s future output is equivalent to that of a fresh instance fed only the records it still has buffered. The default implementation is conservative and says yes only when nothing is pending.

  • reads_payload is the flag. It defaults to False, which declares that your accumulator only ever looks at metadata such as the lane_id and the cursors, and lets the runner leave payloads as unresolved shared-memory handles. Set it to True if push_many inspects payloads and the runner will resolve them first. Forget to, and you get a lazy handle where you expected a dict.

Note that flush() is deterministic in the sense that matters. Its output depends only on the elements the accumulator has seen, never on timing.

Built-in accumulators. PassthroughAccumulator emits whatever arrives, immediately, with no buffering and no state, and the replay filter uses it. CountingAccumulator buffers per lane and emits when a lane reaches max_batch, and it is what most operators use: fetch, decode, tokenize, map transforms, and batching. Batching uses a CountingAccumulator subclass that adds a chunk-aware try_epoch_reset, so a stalled flush sentinel can be released as soon as every pre-boundary record has left the buffer, and that defaults to drop_last=True. Lane keying lives in CountingAccumulator itself, which is what makes a per-lane flush sentinel able to reset one lane alone.

CountingAccumulator can also flush on a latency bound (max_latency_ms), emitting a partial micro-batch rather than waiting for a bursty stream to fill one. There is no global switch that turns this off in deterministic mode. Each built-in operator passes max_latency_ms=None from its own accumulator() when deterministic is set, so its micro-batch boundaries depend only on counts and never on the clock. A custom operator that builds a CountingAccumulator with a latency bound has to do the same: accumulator() receives deterministic, so check it and drop the latency bound when it is True.

The specialized ones ship with the operators that need them, and you never construct one yourself. The accumulator behind pack_sequences keeps per-lane bins and emits when a bin’s remaining capacity drops below the minimum useful sequence length or when too many bins are open. The one behind ensure_mixture keeps per-lane buffers grouped by mixture component and uses smooth weighted round-robin to emit in the order that best tracks the target ratios. shuffle has two, picked by its algorithm argument: a reservoir accumulator for the default "streaming", and a warmup block accumulator for "block_warmup". Plain "block" needs neither: it is a CountingAccumulator with max_batch set to the buffer size, and the shuffling happens on the workers.

How runners keep the order. Beyond the inline, threads and process runners that How pipelines run describes, there is an experimental Ray-backed remote runner for stages you add with placement="remote". From the accumulator’s point of view all four behave identically.

The mechanism behind that is a reorder buffer. Zephon tags each micro-batch with a monotonically increasing sequence number before dispatch, holds out-of-order completions back, and forwards a result only once every preceding sequence number has gone out, so a slow micro-batch that completes after a fast one dispatched later cannot get ahead of it. In non-deterministic mode the runner skips the reordering and forwards results in completion order, trading reproducibility for latency.

Accumulator-defined boundaries plus sequence-number reordering are, together, the reason the execution parameters are pure performance knobs.

Data-derived randomness. The shuffle buffer needs randomness, and the obvious approach would be wrong. An RNG advanced once per micro-batch ties the permutation to micro-batch boundaries, and those boundaries shift across a restart because replay starts from a different point, so the same data would shuffle differently after a resume.

Zephon therefore derives the shuffle’s randomness from the data itself. The block algorithms hash the cursor keys of every element in the batch together with your base seed, while the streaming algorithm derives a per-element salt from the cursor identity and combines it with the seed, the lane, an emission counter and the reservoir size to pick a deterministic victim on each arrival. Either way the same set of elements produces the same result regardless of how they were grouped or which restart they turn up on.

Flush sentinels and stalling. Pipelines containing packing, shuffling or mixture correction use flush sentinels to create the epoch boundaries that make checkpoint eviction safe. Every flush_every_k_chunks chunks per lane, Zephon injects a sentinel that triggers flush(reset=True, lane_id=lane) on each accumulator as it passes. Checkpoint replay and bounded recovery covers why we need them; what follows covers what they mean for an accumulator.

What gets flushed. Every accumulator, scoped to the sentinel’s lane, with one exception noted below. For history-dependent accumulators (preserves_cursor_order=False) the reset is the load-bearing part, while for order-preserving ones the flush is harmless, being either a no-op or a trivial drain, and only the bookkeeping differs:

What “fully reset” means. After flush(reset=True, lane_id=lane), that lane has to be indistinguishable from a freshly constructed accumulator, with its buffers, counters and derived state cleared and every other lane untouched. For the packer that means the lane’s bins are emptied and its partial bins emitted with padding, and for the mixture corrector it means that lane’s deficit weights are reset. This is what lets each lane’s next epoch replay from a clean start.

We enforce the contract rather than assuming it. If flush(reset=True, lane_id=lane) returns while has_pending_data(lane) is still true, the runner raises, because leaving residual cross-boundary state would break replay silently and we would rather fail loudly.

Stalling is deliberately narrow. Exactly one built-in is allowed to hold a sentinel back instead of flushing, and that is batch(drop_last=True), because it cannot emit a partial batch without changing its output. The runner works this out from the operator instance rather than from a trait, which should tell you that it is a special case and not an extension point.

The reason we keep that door shut is worth spelling out. For a general stalled operator, the effective reset point is later than the recorded epoch boundary, so after eviction replay would need the cross-boundary consumption state that determined that delayed point. Zephon checkpoints inflight chunks, epoch boundaries and replay cursors, but it does not checkpoint a general operator replay capsule, and an operator that both reorders and stalls would need one.

batch(drop_last=True) escapes this because it preserves input order, emits only complete batches, and has the replay filter inserted immediately before it by the planner. The consumer-visible checkpoint cut therefore falls between whole batches, so the batch buffer is empty at the replay cursor and nothing extra needs saving. Live execution can still produce a cross-epoch batch like [old, old, new] before the sentinel is released, which is expected and harmless, because on resume the prefix is filtered out before batching and the suffix is rebuilt from an empty buffer at the same boundary.

When the runner sees a sentinel for a stalling accumulator that has pending data on that lane, it skips the flush and holds the sentinel behind the buffered data, releasing it once try_epoch_reset(boundary, lane) succeeds for that lane. Lanes stall independently, so a blocked lane never holds back another lane’s ready sentinel.
