# Direct Vortex reader benchmarks

This is the harness used for the October 2026 local-reader measurements, with
workspace paths externalized and adapters for the historical and current cache
options. The request generator, timing boundaries, warm-up, checksums, and
statistics are retained. It exercises `VortexShard` and format openers; it does
not construct a Pipeline, FetchOp, resolver, or shard-download cache.

All input files must already be local. The tools never access S3. `plan`, `verify`,
and `smoke` collect no timings. `run` requires `--execute-measurements`.

## Workspace

Set `VORTEX_BENCH_ROOT` to a directory on local storage containing:

```text
checkouts/main/          # baseline Zephon checkout
checkouts/candidate/     # candidate Zephon checkout
envs/main/bin/python    # isolated baseline environment
envs/candidate/bin/python
data/manifest.json
data/...                # Vortex shards and per-row fingerprints
```

Install each checkout editable in its respective environment. `requirements.txt`
records the dependencies used in the original comparison (Python 3.12.11).
For example, after creating the two checkouts:

```sh
uv venv --python 3.12.11 "$VORTEX_BENCH_ROOT/envs/main"
uv pip install --python "$VORTEX_BENCH_ROOT/envs/main/bin/python" \
  -r scripts/vortex_bench/requirements.txt
uv pip install --python "$VORTEX_BENCH_ROOT/envs/main/bin/python" \
  --no-deps -e "$VORTEX_BENCH_ROOT/checkouts/main"
```

Repeat for `candidate`. The worker checks that the imported package belongs to
the corresponding checkout. The original comparison used main `31a3dfc0` and
candidate `0f3be0c2`; choose and record revisions for each new comparison.

The manifest has a `shards` list. Each entry contains `dataset` (one of
`fineweb_tokens`, `fineweb_text`, `mammoth`), `path`, `bytes`, `rows`, `sha256`,
`row_hashes`, `row_hashes_sha256`, and `columns`. Paths are relative to the
workspace. `row_hashes` names a JSON list of per-row fingerprints generated by
`common.row_digest`. `columns` maps names to `array:uint32`, `array:uint8`, `str`,
or `int`; these fingerprints compare main's Python lists and candidate NumPy
arrays by value. File digests use `common.file_digest`.

The prepared data is not part of this repository. The original bounded dataset
contained 15,877 token rows, 38,645 text rows, and 87 Mammoth image/text rows.
Images were raw uint8 pixels with dimensions and mode, not JPEG bytes. Reusing
those exact prepared files is necessary to reproduce the reported numbers;
different data measures a different workload. Smoke checks require all three
dataset types and at least 256 rows in each first FineWeb shard.

## Commands and matrix

From the repository root, with the workspace environment variable set:

```sh
uv run --no-project scripts/vortex_bench/bench.py verify
uv run --no-project scripts/vortex_bench/bench.py plan --suite primary
uv run --no-project scripts/vortex_bench/bench.py smoke
```

Timed runs are opt-in:

```sh
uv run --no-project scripts/vortex_bench/bench.py run --suite primary \
  --dataset fineweb_tokens --batch-size 64 --batch-size 256 \
  --seconds 1 --repeats 3 --output "$VORTEX_BENCH_ROOT/results/new-run" \
  --execute-measurements
```

The matrix covers tokens, strings, and images/text; contiguous, shuffled,
random, duplicate, and hot-set requests; retained/reopened readers; individual
and bulk reads; footer/segment cache sizes; and background worker counts.
`primary` compares both revisions. The `cache`, `threads`, and `single_shard`
suites vary the candidate only. Main retains its native cache behavior.

Reads and release of the returned rows are timed. Opener construction and pool
configuration happen before timing. Reopened-reader cases include shard-reader
construction/closure for each request while preserving opener-owned caches.
Warm-up follows the same request sequence on both revisions. OS page caches are
uncontrolled; these are warm local-reader results, not cold-disk or full-pipeline
measurements. Run serially per host and avoid other benchmark activity.

Each run records commits, source hashes, dependency versions, host details,
request-sequence hashes, raw call durations, and value checks. Changing source
during measurement aborts the run. Reusing an output directory is rejected.

## Retained-reader point-read follow-up

The outstanding upstream question is whether a `VortexFile` can retain more of
the preparation used by `scan(indices=...).read_all()` for repeated point reads.
The old `RepeatedScan` path is not used by this implementation. On the original
data, a retained single-text read was 26.4 vs 16.9 microseconds on macOS and
42.2 vs 29.8 on Linux (candidate vs main). These are historical observations,
not measurements of the current commit.

To revisit this, select case
`fineweb_text-getitem-1-random-retained-default-1-round_robin` in the primary
suite using `--case-id`. Compare with the corresponding `reopen` case. This
documents work to discuss with Vortex; no upstream issue has been filed. It
does not require a Zephon reader-lifetime or cache-scope redesign in this PR.
